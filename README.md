# 앱 개발 플레이북

첫 앱을 만들고 배포하면서 실제로 부딪힌 것들을 쌓아 두는 저장소.
튜토리얼 모음이 아니라 **우리가 겪은 것만** 적는다. 겪지 않은 건 적지 않는다.

## 왜 이렇게 관리하는가

앱 개발에서 시간을 잡아먹는 건 코드가 아니라 **한 번씩만 겪는 함정**이다.
키스토어 분실, 정책 거부, 라이선스 문제, 빌드 도구의 조용한 실패 —
전부 두 번째부터는 5분이면 넘어가지만 처음엔 반나절씩 날린다.
그 5분짜리 지식을 남기는 게 이 저장소의 목적이다.

## 대시보드

**https://jinhae8971.github.io/app-dev-playbook/**

전체 문서 검색, 축적된 '신호' 모음, 새 앱 시작 체크리스트가 한 화면에 있다.
문서를 추가하면 워크플로우가 인덱스를 다시 만들어 자동으로 반영된다 —
목록을 손으로 고칠 필요가 없다.

## 기록은 자동으로 남는다

작업 로그는 손으로 적지 않는다. 매일 23:00 KST에 워크플로우가 추적 대상 저장소의
커밋을 모아 `worklog/YYYY-MM-DD.md`로 만든다. `data:` 같은 자동 수집 커밋과
봇 커밋은 걸러낸다.

그래서 **유일한 의무는 커밋 메시지를 제대로 쓰는 것**이다.

```
feat:  기능 추가        fix:   버그 수정
chore: 정리·설정        docs:  문서
data:  자동 수집 (로그에서 제외됨)
```

자동으로 안 남는 것 세 가지는 직접 남긴다. 커밋에는 '무엇을 바꿨나'만 있고
'왜'와 '무엇을 배웠나'는 없기 때문이다.

| 남길 것 | 어디에 |
|---|---|
| 새로 겪은 함정 | `lessons/` |
| 되돌릴 수 있는 결정 | `decisions/` |
| 버전이 올라갔다면 | 해당 저장소 `CHANGELOG.md` |

## 규칙

1. **겪은 것만 적는다.** 검색해서 알게 된 것은 출처를 달고, 직접 확인한 것은
   확인 날짜를 적는다. 이 둘을 섞지 않는다.
2. **정책·요금은 반드시 날짜를 적는다.** Play 정책과 데이터 요금은 자주 바뀐다.
   날짜 없는 정책 서술은 6개월 뒤에 위험한 오답이 된다.
3. **결정은 [decisions/](decisions/)에 남긴다.** 왜 그렇게 했는지를 적어 두면
   나중에 뒤집을 때 근거를 다시 찾지 않아도 된다.
4. **끝난 프로젝트는 [projects/](projects/)에 한 줄 회고를 남긴다.**

## 현재 상태

앱 목록은 [앱 대장](projects/registry.json) 한 곳에서 관리한다.
새 앱을 만들면 여기에 한 줄 추가하면 작업 로그가 자동으로 따라온다.

| 앱 | 단계 | 비고 |
|---|---|---|
| 마켓 히트맵 | 사이드로드 배포, Play 내부 테스트 준비 | 히트맵·산업·트렌드·센티멘트 |
| Cross-Market Flow Radar | 운영 | 웹 전용 |
